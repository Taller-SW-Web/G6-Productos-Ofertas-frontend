# Fronteras contractuales para la selección de componentes de Combos

Este documento registra límites confirmados del contrato; no publica ni consume rutas nuevas.

## Resolución de SKU a producto/variante — `BLOCKED_CONTRACT`

El OpenAPI vigente de Productos publica `GET /productos` con búsqueda `q` sobre nombre y descripción, y `GET /productos/{productoId}/variantes`, que requiere conocer previamente el `productoId`. No existe operación publicada para resolver varios SKU directamente. El frontend no recorre el catálogo para simular esa API: mantiene un caché local de hasta 500 SKU de productos/páginas y fichas ya leídas, con TTL de 30 segundos y evicción FIFO. Un SKU no observado sigue sin resolver; la presentación conserva el texto del SKU y no afirma que sea inexistente. Para grandes catálogos la resolución autoritativa por SKU permanece `BLOCKED_CONTRACT`.

### Propuesta para el owner de Catálogo

Publicar una operación de resolución batch con límite máximo de 100 SKU y respuesta explícita por SKU, por ejemplo:

```http
POST /api/v1/productos/resolucion-skus
Content-Type: application/json
```

```json
{ "skus": ["SKU-1", "SKU-2"] }
```

La respuesta debería incluir `items` con `sku`, `product_id`, `product_name`, `producto_estado`, `es_variante`, `estado_variante` y `tipo_producto_id`, más `no_encontrados`; la semántica de orden y duplicados debe fijarse en OpenAPI. Debe ser lectura idempotente, no exponer inventario ni precios, y conservar resultados parciales sin confundir inexistencia con error. El owner de Catálogo y Arquitectura deben aprobar ruta/payload y publicar contrato y pruebas de provider. La operación solo puede habilitarse para el navegador con `userBearer`/scope `catalogo:leer` permitido al cliente; cualquier consumidor de servicio espera registro de scope y allowlist G7. La ruta y DTO anteriores son una propuesta, no un contrato existente.

## Filtrado de tipos y total de página — `BLOCKED_CONTRACT`

La búsqueda de productos usada por Combos no publica un filtro por tipo. Filtrar localmente los elementos altera la relación entre filas, total y paginación. El editor conserva la página y total del provider, marca los productos cuyo tipo publicado coincide con un tipo Combo como no seleccionables y vuelve a validar identidad al elegir. Para devolver páginas compuestas solo por candidatos se requiere que Catálogo publique el filtro; el frontend no descargará el catálogo completo para reconstruirlo.

### Propuesta para el owner de Catálogo

Agregar un query opcional a `GET /api/v1/productos`:

```text
tipoProductoIdExcluido=<UUID>&pagina=<entero 1-based>&tamanio=<1..100>
```

El provider debe aplicar el filtro de tipo **antes** de ordenar, paginar y contar; el `total` debe ser el total posterior al filtro, estable para la misma consulta/snapshot, y `items` debe contener solo candidatos elegibles. El filtro debe componerse con `q`, estado, categoría, canal y demás filtros ya publicados. Respuesta: el mismo envelope publicado de catálogo (`items`, `meta.pagina`, `meta.tamanio`, `meta.total`) con productos tipados, sin campos derivados desde el cliente. El provider valida UUID/tamaño, retorna error de validación para valores inválidos y mantiene los errores estándar 401/403/429/500/503. La operación no cambia permisos: mantiene `api-productos` y `catalogo:leer`, requiere registro de scope G7 y allowlist del cliente navegador antes de su uso. Owner: Catálogo backend + Arquitectura/API; el owner de Combos entrega los identificadores de tipo autorizados, no nombres. Homologación: actualizar OpenAPI, confirmar semántica/índice de base de datos, prueba provider para total filtrado y páginas límite, prueba de autorización G7 y prueba de integración frontend con combinaciones filtro+búsqueda. Hasta esa homologación el filtro no se consume y se mantiene `BLOCKED_CONTRACT`.

## Precio vigente — contrato existente consumido

`GET /api/v1/precios?skus=...` está publicado en `../docs/contratos/http/openapi.yaml` como batch de hasta 100 SKU. Combos omite `canal` para solicitar el alcance global y conserva literalmente `currency` y `channel_id`; las reglas de comparación actuales aceptan el dominio PEN y `channel_id=null`, así una respuesta con otro canal/moneda queda no comparable y no se maquilla. También conserva `valid_from`, `valid_until`, `price_version`, `vigencia_id`, `origen` y SKU. El contrato documenta `PRECIO_NO_ENCONTRADO` en `GET /api/v1/precios/skus/{sku}`; se usa esa operación para SKU que contienen coma, que no pueden representarse sin ambigüedad en la lista CSV. Una respuesta batch omite precios ausentes como establece la respuesta `items`; el frontend no fabrica registros.

La revisión del OpenAPI indica `x-scope-registration-status: pending-security-registration` para `precios:leer` y `catalogo:leer`. Esto es una dependencia de configuración de autorización G7 y no se resuelve con un token de servicio en el navegador.

## Creación idempotente de Combos — `BLOCKED_CONTRACT`

El frontend conserva `POST /api/v1/combos/administracion`, que valida el usuario `GESTOR_COMERCIAL`, exige `Idempotency-Key` y permite reconciliar el mismo alta tras perder el recibo. El OpenAPI actual publica `POST /api/v1/combos`, pero la inspección del backend confirma que esa operación no consume la clave idempotente. Cambiar a la ruta publicada debilitaría la garantía ante timeouts y duplicados; presentar la ruta administrativa como contrato publicado también sería incorrecto.

**Owner de resolución:** owner de Combos backend + owner del OpenAPI/Arquitectura + Seguridad G7. Deben publicar una sola operación autorizada que combine el rol/permiso de gestión y la semántica documentada de `Idempotency-Key`, o documentar formalmente el endpoint administrativo existente con su payload/respuestas/seguridad. Desbloqueo solo tras publicar el contrato, validar autorización G7 y pasar pruebas del provider; hasta entonces se mantiene la operación segura actual y la creación API permanece `BLOCKED_CONTRACT`.

### Optimizaciones ejecutadas y límites que permanecen

- B1: lectura de lista/detalle ya no espera `GET /combos/{id}/disponibilidad` por cada registro. Se usa el DTO principal (`informative_availability`, `calculated_at`, `freshness`); null se mantiene null. Solo cero con frescura `ACTUALIZADA` y timestamp válido se presenta como agotado.
- B2: en adapter API `resolveSkus` solo consulta el caché acotado de filas/fichas ya leídas; no dispara una petición de red ni recorre el catálogo. Hasta 500 entradas, TTL 30 segundos, FIFO y poda de expiradas; un miss no significa SKU inexistente y se conserva el SKU crudo como fallback. El escaneo de catálogo queda disponible únicamente en el runtime de fixtures mock, habilitado explícitamente en `createMockCombosRuntime`, y nunca en el adapter HTTP. La resolución autoritativa API permanece bloqueada hasta homologar la propuesta SKU→producto de arriba.
- B3: precios batch reales, sin canal (global), conservan moneda, canal efectivo, vigencia, versión y origen. Precios ausentes no se inventan; SKU con coma usan el endpoint individual publicado. No usar un servicio bearer en el navegador.
- B4: `listProducts` conserva la página y total íntegros; tipos Combo publicados se muestran inhabilitados. No se reconstruye el total con filtro cliente ni se descarga el catálogo completo para poblar el selector.
- B5: el valor raw cambia la identidad visible inmediatamente; la consulta se mantiene debounced 250 ms. Se conserva la selección al alternar búsqueda/página y se valida de nuevo contra el resultado antes de agregarla.
- Carga/resolución duplicada previa: cada item listado/detallado invocaba una resolución que recorría productos y variantes y una disponibilidad auxiliar; con N combos se multiplicaban lecturas de catálogo y llamadas de disponibilidad. B1 elimina la disponibilidad auxiliar; B2 elimina el barrido y limita enriquecimiento a datos ya observados. En detalle la resolución/cálculo de stock no pasaba un `AbortSignal`; se corrigió para cancelar al desmontar/cambiar combo. La disponibilidad de Inventory real sigue siendo `NO_VERIFICABLE` en el adapter API, que devuelve `stock: null` sin llamar a Inventory.
